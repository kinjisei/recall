# Бэкапы: как устроены и как восстановить

> Читать в спокойный день, а не в тот, когда всё сломалось.

## Что происходит само

Каждую ночь в 09:00 по Алматы GitHub Actions запускает
`.github/workflows/backup.yml`:

1. подключается к базе строкой из секрета `SUPABASE_DB_URL`;
2. снимает полный дамп (`pg_dump`) — все таблицы и данные;
3. сжимает и **шифрует** его паролем из секрета `BACKUP_PASSPHRASE`;
4. кладёт файл вида `recall-2026-08-08.sql.gz.gpg` в артефакты прогона.

Дамп первого числа месяца хранится 90 дней, остальные — 14.

**Почему шифруем.** В дампе лежат данные учеников: почты, имена, слова,
сданные работы, переписка с AI в квестах. Артефакт — это файл на чужих
серверах. Без шифрования любой, кто получит доступ к репозиторию, получил бы и
всю базу.

## Где взять файл

GitHub → вкладка **Actions** → слева **Бэкап базы** → выбрать нужный прогон по
дате → внизу страницы блок **Artifacts** → скачать.

## Как восстановить

Понадобится `gpg` и `psql`. На Windows проще всего через WSL или Git Bash с
установленным PostgreSQL.

**Шаг 1. Расшифровать и распаковать.**

```bash
gpg --decrypt recall-2026-08-08.sql.gz.gpg > recall.sql.gz
gunzip recall.sql.gz
```

`gpg` спросит пароль — это `BACKUP_PASSPHRASE`.

**Шаг 2. Посмотреть, что внутри, ПРЕЖДЕ чем заливать.**

```bash
head -50 recall.sql          # шапка дампа
grep -c "INSERT INTO" recall.sql   # сколько строк данных
```

Если файл подозрительно мал или пуст — не заливайте: возможно, сломался сам
бэкап, и вы затрёте живую базу пустотой.

**Шаг 3. Залить.**

⚠️ Дамп снят с флагом `--clean --if-exists`: **он удаляет существующие таблицы
перед созданием заново**. То есть заливка в рабочую базу сотрёт всё, что
появилось после снятия дампа.

Поэтому по умолчанию восстанавливать нужно **в новый проект Supabase**, а не
поверх рабочего:

```bash
psql "postgresql://postgres.НОВЫЙ_ПРОЕКТ:ПАРОЛЬ@aws-1-eu-central-1.pooler.supabase.com:5432/postgres" -f recall.sql
```

Поверх рабочей базы — только если данные уже потеряны и терять нечего.

## Что делать, если бэкап упал

Прогон падает громко и с текстом. Частые причины:

- **«Нет секретов»** — не заведён `SUPABASE_DB_URL` или `BACKUP_PASSPHRASE`.
- **Ошибка подключения** — сменился пароль базы. Обновите секрет
  `SUPABASE_DB_URL` (Supabase → Connect → Session pooler).
- **«Дамп подозрительно мал»** — подключение прошло, но данных не пришло.
  Проверьте строку: возможно, взят Transaction pooler (порт 6543) вместо
  Session pooler (5432).

## Чего этот бэкап НЕ покрывает

- **Аккаунты входа.** `pg_dump` снимает схему `public`. Пароли и сессии живут в
  служебной схеме `auth`, которую Supabase на бесплатном тарифе выгружать не
  даёт. При восстановлении в новый проект люди заведутся заново по почте, но
  пароли придётся сбрасывать. Данные (слова, работы, программы) при этом целы.
- **Файлы в Storage** — мы им не пользуемся, но если начнём, бэкап нужно будет
  расширить.

## Проверка, что всё живо

Раз в пару месяцев стоит скачать свежий артефакт и пройти шаги 1–2. Бэкап,
который ни разу не открывали, — это надежда, а не бэкап.
