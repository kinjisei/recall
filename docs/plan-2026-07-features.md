## Definition of Done (вшивается в КАЖДЫЙ заход — не «для галочки»)
1. **Соседи и стыки.** Grep всех, кто вызывает изменённое (функция/компонент/тип).
   Каждая новая кнопка/ссылка — явно проверить, ЧТО открывает и КУДА ведёт. Общий
   паттерн — править во ВСЕХ местах, не в одном экране.
2. **Данные честно.** Живой тест на реальных данных (превью-сборка или прод), не
   «выглядит правильно». AI — прогон на проде с настоящей моделью.
3. **Регрессия рядом.** Прогнать смоуки соседних фич (список — в каждом заходе).
4. **Стоимость/лимиты.** Каждое новое AI-действие: какой класс (light/heavy),
   сколько стоит, не жжёт ли чужой карман квоты.
5. **Сборка + деплой.** `npm run build` чисто → коммит ТОЛЬКО своих файлов (не
   цеплять чужую работу параллельных сессий) → push → убедиться, что прод реально
   обновился (проверить контент-хэш чанка ≠ старый; НЕ сверять с локальным хэшем —
   Vercel даёт свой) и фича работает.
6. **Белые дыры.** В конце — список «что осталось непокрыто / что может сломаться»,
   а не молчание.

## Заход 3e — доработка «Разобрать весь текст»: уровень-диапазон + больше находок + never-empty
**Контекст.** Диагностика (2026-08-02): база НЕ врёт (тексты размечены верно),
но движок `lib/textAnalysis.ts` занижает уровень — он **усредняет** уровни кусков
(финальный уровень — отдельный запрос по списку уровней кусков, при сбое
`mostCommon`). Текст «простое начало + сложный конец» получает A2, хотя находки
в нём реально B1+. На проде текущий промпт стабильно даёт B1+находки (4 прогона),
т.е. пустой/A1 у пользователя — разовый сбой слабой фолбэк-модели; но схема хрупкая.
**Решения пользователя (2026-08-02):**
- Уровень — **по самым сложным местам, не по среднему**; показывать **диапазоном**
  («B1–B2, сложнее к концу»).
- Находки — **сортировать по полезности** (ценное сверху).
- **Без жёсткого лимита** находок («столько, сколько реально примечательного, но
  не топи в мелочи») — вместо нынешних «макс 8 на кусок».
**Сделать.**
1. *Уровень-потолок + диапазон.* Финальный уровень считать **в коде** как максимум
   по кускам (шкала A1<A2<B1<B2<C1), а не запросом. Диапазон: нижняя = медиана/мода
   кусков, верхняя = пик; если пик в одном куске из многих — показываем «X–Y,
   сложнее к концу/местами». В каждый кусок-промпт добавить **рубрику CEFR**
   (A1=Present Simple/частотное; A2=Past Simple/going to; B1=кондишн-1/герундий-
   подлежащее/require·effective·willpower; B2=перфект-континиус/пассив/кондишн-2-3/
   абстрактное; C1=инверсия/идиоматика/редкое), чтобы замер куска был точным.
   Шаг `synthesize` **перестаёт решать уровень** — только `why` (объясняет диапазон:
   «большая часть B1, концовка B2») + `takeaway`, уже под посчитанный уровень.
2. *Больше находок + сортировка.* Снять `max=8`: промпт «столько, сколько реально
   примечательного, без мелочи»; `parseAnalyzedItems` — без жёсткой обрезки (или
   мягкий потолок ~20/кусок как предохранитель от вываливания). Модель отдаёт
   находки **по убыванию полезности**; порядок сохраняем при дедупе.
3. *Never-empty.* Промпт: СНАЧАЛА примечательное под уровень текста; если мало —
   ДОБРАТЬ полезными словами уровня + разбор главной грам-структуры; **без
   выдумывания** несуществующих фраз. Плюс страховка в пайплайне: пустой список
   находок → повтор/фолбэк, чтобы UI на реальном тексте не писал «ничего не нашлось».
**Соседи/стыки.** Тип `TextAnalysis.level` станет диапазоном — обновить
`TextAnalysisSheet` (показ «B1–B2») и кэш `textAnalysisCache` (формат не ломать —
старые ключи просто перечитаются). `mostCommon` в `lib/textChunks` больше не нужен
для уровня (оставить, если используется ещё где). Одиночный разбор предложения
(`analyze.ts`/AnalysisSheet) уровень НЕ показывает — его не трогаем, но рубрику/
сортировку/лимит унести в общий код, чтоб не разъехалось. При большом числе находок
`AnalyzedItemsView` уже группирует — проверить, что 20+ строк не ломают вёрстку
(сворачивание/скролл).
**Живой тест (прод, E2E).** «Small habits» → диапазон включает B1 (не A1),
находки непусты и отсортированы; короткий A1-текст → A1 и всё равно непусто;
намеренно смешанный текст (простое начало + C1-концовка) → верхняя граница ≥ B2.
Прогнать 3× — разброс уровня в пределах соседней ступени.
**Workflow.** нет (промпты — сам, живым прод-тестом; дешёвой моделью нельзя —
качество уровня критично).
**Стоимость.** AI-действий столько же (цена = куски+1; лимит находок токены, не
запросы; уровень теперь в коде — синтез остаётся 1 запрос на why/takeaway).
**Регрессия.** `test-textchunks.mjs` (резка не тронута); ручной прод-прогон
нескольких встроенных текстов EN/ES — метка приложения vs диапазон разбора близки.

## Заход 5b — «Письмо»: ученица пишет + AI-оценка + самопересдача
**Сделать.** Экран написания у ученицы (поле, подгрузка прошлого текста из attempts,
счётчик слов). Сдача → AI-оценка (`lib/writingGrade.ts`): IELTS (бэнд+4 критерия) или

результата ученице. Ученица может САМА править и пересдавать, пока не проверено
(каждая сдача = её heavy). Каждая сдача пишется в attempts (история).
**Соседи/стыки.** Переиспользовать промпт/логику режима «Письмо» из Диалога
(`writingSystemPrompt`, task `writing`). Структурный список ошибок — тот же формат,
что упражнения (для по-строчной проверки в 5c). Чек-листы целевых слов — сверять с
настройками задания.
**Живой тест (прод).** Оба режима: написать → оценка приходит и осмысленна (IELTS
бэнд+критерии; Обычный чек-листы верно отмечают употреблённые слова/грамматику);
самопересдача создаёт новую попытку, прошлый текст подгружается.
**Workflow.** ✅ Регрессия оценки: воркфлоу гоняет оценку на 4-5 эссе разного уровня
(дешёвый проверяющий: бэнд адекватен уровню, ошибки реальны, чек-листы совпадают с
целевыми словами). ⚠️ но само эссе-оценивание — heavy-модель; проверяющий — дешёвый.
**Стоимость.** 1 heavy за оценку и за каждую самопересдачу.
**Регрессия.** `smoke-writing.mjs` расширить (сдача→оценка).
