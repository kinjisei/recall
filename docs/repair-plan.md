## Правила качества (действуют на каждом этапе)

1. **Чиним класс, а не экземпляр.** Нашли кривой возврат в читалке — проверяем
   все экраны с тем же приёмом. Это прямое требование владельца.
2. **Замер вместо мнения.** Утверждение «стало лучше» подтверждается числом:
   тапами, пикселями, записями в истории, ответом RPC.
3. **Сначала докажи, что сломался тест.** За пять ревью 12 «багов продукта»
   оказались артефактами инструмента. Прежде чем править код — перепроверь
   другим способом.
4. **Никаких правок лимитов без обхода текстов.** Дважды за один день обещания
   расходились с кодом: правь `schema.sql` — иди в `lib/billing.ts`,
   `PricingPage.tsx`, `LegalPage.tsx`, подписи форм.
5. **Каждый этап заканчивается зелёной сборкой, смоуками и живым прогоном.**
   Пуш — только после этого.
6. **Параллелим по непересекающимся файлам.** Общие точки (`App.tsx`, роуты,
   `Layout`, `index.css`) правлю сам, чтобы не ловить конфликты слияния.

# ЭТАП 1 🔴 Навигация: приложение должно уметь «назад»

Три из четырёх красных находок ревью 1Г плюс первая находка 1А. Бьёт по всем без
исключения, а в установленном на телефон PWA свайп-назад — единственный способ
вернуться.

### 1.1 Внутренние экраны — в адрес

**Где.** ~20 файлов с внутренним `useState` вместо адреса. Правильный образец
уже есть — «Практика» с `?m=`.

**Промпт:**
```
Роль: разработчик Recall (читай CLAUDE.md и docs/ARCHITECTURE.md — контракты не ломать).

Контекст. Ревью навигации (docs/mkt/20-ux-review-1g-navigation.md) замерило:
больше половины внутренних экранов не существует для истории браузера. «Назад» из
открытого текста ведёт на Главную мимо списка и хаба; из упражнений задания — на
Главную с обнулёнными ответами. В PWA на телефоне свайп-назад — единственный способ
вернуться. Образец правильного решения уже в коде: PracticePage хранит режим в
адресе (?m=), и там всё работает.

Задача. Перевести внутреннее состояние «где я нахожусь» из useState в адрес для
экранов: ReaderPage (открытый текст), SpanishReader, AssignmentsPage (задание и
стадия), GrammarPage (урок), QuestsPage (чат квеста), StudyPage (view),
MaterialsSection и ReviewScreen (режим), TeacherPage (вкладка), игры в
features/words (какой режим открыт).

Ограничения:
- Адресуемо МЕСТО, а не ход раунда. Прогресс спринта/диктанта после F5 начинается
  заново — это правильно, не пытайся его сохранять.
- Смена внутреннего экрана = replace или push осознанно: заход внутрь пушит запись,
  возврат кареткой — НЕ пушит (сейчас пушит, и свайп-назад возвращает в «Спринт»).
- Идентификаторы в адресе должны быть устойчивы (id текста/урока/задания), чтобы
  ссылка «прочитай вот это» работала завтра.
- Несуществующий id в адресе → осмысленный экран, не пустой и не белый.
- useScrollTop и useSmartBack уже есть — используй их, не пиши свои.

Критерии приёмки: npm run build чистый; scripts/smoke-navigation.mjs проходит для
КАЖДОГО перечисленного экрана (открыть → назад → оказался на шаг назад, а не на
Главной); F5 на каждом экране оставляет на нём же; 20 глубоких ссылок из отчёта
1Г по-прежнему открываются. Коммит без пуша.
```

### 1.3 «Начать первое занятие» ведёт в меню

**Где.** `OnboardingFlow.tsx` + `lib/guided.ts`.

**Промпт:**
```

# ЭТАП 2 🔴 Деньги и честность отказов

Бьёт по платящим — по тем, кто уже дал денег. Требует **заливки SQL**.

### 2.1 Энергия сгорает, когда AI не ответил

**Подтверждено сегодня по коду:** в `api/gemini.ts:99` энергия списывается
*до* обращения к модели (строка 128). Если вся цепочка моделей выгорела по
суточным квотам Google, человек теряет ⚡ и не получает ничего.

**Промпт:**
```
Роль: разработчик Recall.

Контекст. api/gemini.ts вызывает authorize() (списывает энергию) ДО callGemini().
При выгорании всей цепочки моделей (429 у каждой) пользователь теряет энергию и
получает отказ. Это бьёт по платящим и читается как поломка продукта, хотя
ограничение — внешнее, со стороны Google.

Задача.
1. Добавить в schema.sql RPC refund_ai_call (security definer): снимает последний
   записанный вызов пользователя, если запрос не дошёл до модели. Защита от
   злоупотребления: снимать только вызов, созданный этим же пользователем в
   последние N секунд.
2. Вызывать её из api/gemini.ts при провале ВСЕЙ цепочки. Если запрос дошёл до
   модели и та ответила — энергия остаётся списанной, это честно.
3. Развести два случая в текстах: «у тебя закончилась энергия» (наш лимит,
   вернётся утром) и «AI сейчас недоступен» (не твоя вина, энергия не потрачена).
   Проверить, что клиент их РАЗЛИЧАЕТ и показывает по-разному.
4. Текст внешнего отказа: что произошло, что работает как обычно (чтение, слова,
   грамматика, произношение), когда пробовать снова. Без слова «ошибка».

Ограничения: блок SQL идемпотентный, в конце файла, с комментарием-заголовком;
перед выдачей владельцу прогнать scripts/validate-schema-dryrun.mjs.

Критерии приёмки: смоук, эмулирующий отказ всей цепочки — энергия НЕ списана,
текст корректный; смоук на успешный вызов — энергия списана ровно один раз;
build. Коммит без пуша.
```

# ЭТАП 4 🟡 Качество AI и корректность механик

### 4.1 Промпты: исправления, которых не было

**Промпт:**
```
Роль: методист и разработчик Recall.

Контекст (замеры из docs/mkt/20-review-2b-ai-quality.md):
- Диалог иногда сдвигает время в исправлении: «he don't like → he DIDN'T like» там,

- Выдумал ошибку в корректной фразе: «too → [удалить]» в «My sister works in a

Задача. Правки промптов: (1) исправлять ТОЛЬКО грамматику, не менять время и смысл

(3) каждое исправление в «улучшенной версии» обязано быть в списке разбора.

Критерии приёмки: повторный прогон тех же трёх сценариев (не более 6 тяжёлых
вызовов) — сдвига времени нет, выдуманных ошибок нет, список совпадает с текстом.
Генерацию материалов и программ НЕ трогать: дорогая Pro-квота.

### 4.2 Счётчики и фильтры

- MCQ с дублирующимися вариантами: клиент считает по индексу, сервер по тексту.
- `profiles.level` по умолчанию `'B1'` — новичок до теста общается с AI как B1, а
