### 3. Опасные места для перехода на миграции

Порядок блоков в файле принципиален и почти нигде не документирован явными
номерами — только относительным «выше/ниже» в комментариях. Ключевые
зависимости (все — цитаты из самого файла):

1. **Два revoke-рубежа, и порядок между ними значим.** Строка `:2712-2713`:
   `revoke execute on all functions in schema public from public, anon; grant
   execute … to authenticated;` — действует только на функции, СУЩЕСТВУЮЩИЕ на
   этот момент выполнения файла. Строка `:4057-4070`: `do $harden$` — цикл по
   `pg_proc`, снимает EXECUTE у public/anon со всех функций, кроме
   `track_event` (`:4072`) — обязана быть **последней** в файле. Всё, что
   объявлено МЕЖДУ рубежами (`:2732`–`:4023` — вся энергия, домашка,
   `admin_feedback`, `assign_words_to_student`, `delete_my_account`),
   полагается на финальный блок, а не на revoke из середины. Разбить файл на
   независимые миграции — значит на каждом промежуточном шаге либо не иметь
   финального блока (новые функции открыты anon/public по умолчанию
   Postgres/Supabase), либо иметь его не последним (тогда он не накрывает то,
   что создано после). Живой урок из самого файла (`:4037-4042`):
   `choose_homework_item` была открыта анониму «одно окно между заходами»,
   `submit_word_check` — систематически, из-за `drop function` (п.4) ниже
   рубежа `:2712`.

2. **Поимённые revoke/grant разбросаны точечно ПОСЛЕ рубежа `:2712`** —
   `:2864-2866`, `:2901-2908`, `:2959`, `:3111-3116`, `:3173`, `:3225`,
   `:3441-3444`, `:3920-3937`. Каждый блок вручную повторяет «после общего
   revoke функции нужен грант поимённо» — порядок кусков в файле УЖЕ сейчас
   определяет корректность прав, и миграции обязаны переносить этот инвариант,
   а не только текст функции.

3. **Колоночные гранты `profiles`** объявлены в ТРЁХ разнесённых местах
   (`:571-572` update-триплет, `:1780-1782` select-список с предварительным
   `revoke select`, `:2987-2989` тот же список +`goal`, `:4005-4006` отдельный
   `grant select/update (es_level)` без общего revoke). Postgres
   `GRANT … (col)` аддитивен, поэтому итоговый набор колонок — это
   ОБЪЕДИНЕНИЕ всех grant-строк по ходу файла. Базовая миграция обязана
   вычислить это объединение один раз, иначе легко воспроизвести только
   последний по тексту блок и потерять более раннюю колонку.

4. **`drop function` + `create or replace` вместо чистого `create or replace`**
   встречается при смене типа возврата: `submit_word_check` (`:796`, boolean→
   jsonb), `consume_ai_quota()` без аргументов (`:1938`), `spend_energy` (`:2760`,
   добавлен 4-й параметр). Сам файл называет это классом ошибки (`:4040-4042`):
   такая функция при КАЖДОЙ полной заливке на мгновение получает права по
   умолчанию — без блока-страховки в конце она оставалась бы открытой анониму
   навсегда. Миграции, применяемые по одной, воспроизводят это на каждом шаге:
   если в цепочке нет финального harden-шага, любая migration с
   `drop function` открывает окно.

5. **Функции, ссылающиеся на ещё не созданную колонку, обязаны идти строго
   после `alter table … add column`.** Пример из комментария (`:2433-2435`):
   `covering_teacher` читает `teacher_students.seat`, и колонка заведена
   ИМЕННО ПЕРЕД функцией — «функции на language sql проверяются при создании,
   ссылка на не существующую колонку валит всю заливку (ERROR 42703)». При
   нарезке на миграции порядок файлов обязан сохранить это отношение буквально
   по строкам, не по смысловым блокам.

6. **Одноразовые `do $mig$ … end $mig$` блоки с guard'ом** (`:2558-2572` —
   простановка `seat` по умолчанию; `:3394-3439` — перенос `deck_assignments`

  литералами, а не импортом константы (осознанно: «падает при сдвиге эффекта,
  а не константы»).
- `check-schema-equal.mjs` — слепок каталога Postgres (функции с исходниками,
  политики, гранты, колонки, индексы, триггеры), построчное сравнение; по
  описанию трижды ловил реальные потери при сжатии файла.
- `check-anon-access.mjs` — читает `pg_proc.proacl` напрямую, краснеет в обе
  стороны (лишнее открыто И `track_event` случайно закрыт).
- `smoke-wordcheck.mjs`, `smoke-atomic.mjs` (`replace_study_plan`) — шлют
  ПОДДЕЛЬНЫЙ вердикт/параметр и проверяют отказ сервера, не только happy path.

**Подозрительно слабые места:**
- `smoke-open-registration.mjs` — проверяет состояние, переключаемое ОДНИМ
  ручным SQL за всё время жизни проекта; корректен по конструкции, но почти
  никогда не упражняет вторую ветку в проде.
- `test-sentence-around.mjs` — сверяет копию функции с собой же (дублирует
  тело `sentenceAround` вручную, сам предупреждает о рассинхронизации); слеп
  именно к тому классу регрессии, для которого написан — расхождению с
  оригиналом в `.tsx`.
- `smoke-basepacks.mjs` — заголовок и комментарии скопированы из
  `smoke-idioms.mjs` почти без правок («UI-смоук идиом», инструкция запускать
  `smoke-idioms.mjs»); функциональность рабочая и отдельная, но вводит в
  заблуждение при чтении.
- `smoke-markwords.mjs` vs `smoke-mytexts.mjs` — один и тот же сценарий
  (вставка текста → выделение → карточка); `smoke-mytexts.mjs` новее (PDF
  генерируется на лету, а не тянется из внешнего файла), `smoke-markwords.mjs`
  похож на оставленный предыдущий заход, который не удалили.
- `shot-content.mjs` — не проверка (визуальный дамп для человека), путь
  вывода зашит в `scratchpad` конкретной ЗАВЕРШЁННОЙ сессии Claude Code —
  сейчас упадёт на записи в несуществующую директорию, то есть падает по
  случайной причине, а не «по делу».
- `check-dialog-prompt.mjs` — рабочий, но зашивает абсолютный путь
  `d:/projects/recall-app/.env.local`, без заголовка/комментария — ручной
  инструмент отладки, не воспроизводимая проверка, ни в каком CI.

### 7. Что покрыто плохо или никак — по доменам

- **Чат/диалог (`conversations`/`messages`)** — RLS проверяется только
  косвенно через `smoke-chat-history.mjs` (UI); запись идёт прямыми CRUD без
  SD-прослойки (единственный такой домен) — нет отдельного «RLS-смоука» по
  образцу `smoke-writing.mjs`/`smoke-placement.mjs`.
- **`consume_ai_quota` vs `spend_energy`** — состояние объявлено переходным
  (§2), но ни один скрипт не проверяет, что ИМЕННО стоит на пути
  `/api/gemini` (это в `api/*.ts`, вне периметра schema-скриптов) — риск, что
  один из путей орфанный и проверками не закрыт.
- **Актуальность `database.types.ts`** — ни один скрипт не сверяет
  сгенерированные типы со схемой (drift на 30 функций/5 таблиц, §2);
  `check-api-vercel.mjs`/`npm run build` проверяют компиляцию, но не то, что
  типы СООТВЕТСТВУЮТ базе — расхождение прячется за `as unknown as`.
- **`assign_selected_words`/`deck_assignments`** — единственная проверка
  (`smoke-atomic.mjs`) держит живым путь, который продукт уже свернул; нет
  проверки ОБРАТНОГО факта — что `deck_assignments` в проде пуста.
- **Парные правила клиент/сервер вне `answerMatches`** — `norm_typed` (SQL) и
  клиентская нормализация проверяются только для печатных ответов
  (`test-answermatches-sql.mjs`, вне CI, требует БД); для других
  задокументированных «двух копий одного правила» (например,
  `homeworkRows`/`get_homework_many` — «форму строит тот же `homework_json`»)
  отдельного теста на СОВПАДЕНИЕ нет, только косвенно через `smoke-homework.mjs`.
- **Резервное копирование** — `backup.yml` проверяется юнитами
  (`test-backup-precheck`, `test-backup-explain`), но ни один скрипт не
  проверяет ВОССТАНОВЛЕНИЕ из дампа, только снятие.
- **CI не гоняет ни одного smoke-* и ни одного live-check** — `checks.yml`
  осознанно ограничен тем, чему не нужна база или браузер (`:7-10`); вся
  RLS/RPC-поверхность (48 политик, 82 функции) проверяется ТОЛЬКО вручную
  локально. Для перехода на миграции и тестовую базу это прямая точка риска:
  правка миграции может тихо сломать RLS без красной лампочки в PR.

## Сквозные наблюдения

1. Схема физически ОДИН файл на 4073 строки без модульных границ (кроме
   комментариев-заголовков `-- ====`), при этом уже содержит два разных
   механизма идемпотентности (`do $$ … end $$` пронумерованные «этапы» и
   голые блоки без обёртки) — переход на миграции потребует решить, что
   именно становится границей файла: смысловой блок или дата.
2. Права функций и колонок собираются из НЕСКОЛЬКИХ мест по всему файлу
   (§3, пп. 2–3) — это самое трудоёмкое для механического переноса в
   набор миграций, потому что итоговое состояние не читается из одного
   места, а вычисляется «по ходу выполнения».
3. `database.types.ts` реально устарел относительно `schema.sql` (30 функций,
   5 таблиц) при этом компилируется без ошибок благодаря `as unknown as` —
   типобезопасность для трети функций схемы сейчас декоративна.
4. Ни разу не встретился случай, когда RLS-политика опирается на секретную
   колонку без грант-обхода — принцип «RLS не прячет колонки» соблюдается
   последовательно везде, где были найдены секреты (`profiles`, `ai_calls`,
   `events`, `allowed_emails`).
5. CI (`checks.yml`) сознательно исключает всё, что требует базы или
   браузера — 69 из 86 скриптов существуют ВНЕ автоматического прогона и
   зависят от дисциплины разработчика.
6. Список тестов в `checks.yml` — литеральный, без wildcard; новый
   `test-*.mjs` не подхватывается автоматически (риск того же класса, что и
   ручные `grant`-повторы в схеме — «забыли дописать»).
7. Обнаружены минимум два «полу-дубликата» смоуков одного сценария
   (`smoke-basepacks`/`smoke-idioms`, `smoke-markwords`/`smoke-mytexts`) —
   похоже на артефакты последовательных заходов, не подчищенные после
   переименования фичи.
8. Один явно мёртвый путь БД (`assign_selected_words` + `deck_assignments`)
   держится живым ИСКЛЮЧИТЕЛЬНО проверкой (`smoke-atomic.mjs`), которая сама
   и есть единственный оставшийся вызывающий.
9. Часть «одноразовых» скриптов (`shot-content.mjs`, `check-dialog-prompt.mjs`,
   `gen-icons.mjs`) хранится в общем `scripts/` наравне с воспроизводимыми
   проверками — при переносе в новую структуру их придётся явно разделить по
   назначению, иначе они продолжат выглядеть как часть регрессионного набора.
10. Обе «живые» схемные проверки (`check-schema-equal.mjs`,
    `validate-schema-dryrun.mjs`) требуют тестовую базу уже СЕЙЧАС — то есть
    инфраструктура для будущего перехода на миграции частично существует
    (умеет прогонять SQL в транзакции и сравнивать каталоги), просто ещё не
    нацелена на пошаговые миграции, а на файл целиком.

  рабочей копии, или там уже накопилось расхождение — правило проекта
  «сначала schema.sql в Supabase, потом push» предполагает синхронность, но
  сам этот документ её не проверяет (это живая проверка, а задание запрещало
  ходить в базу).

  зашифрованного бэкапа (`backup.yml`) — не выяснено, тестировалось ли это
  вручную владельцем хоть раз.
