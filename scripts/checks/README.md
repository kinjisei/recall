# Сторожа — что проверяется автоматически

Единый стандарт кода держит проверка, а не память (журнал п.3, 8, 17;
архитектура §2, §10). Сторожа работают в трёх местах:

| Где | Что запускается |
|---|---|
| перед коммитом (хук `pre-commit`) | линтер и секреты по файлам коммита, границы, токены, размер, план, блоки описаний |
| сообщение коммита (хук `commit-msg`) | описания |
| `npm run check` | всё по всему коду + описания неотправленных коммитов |
| CI (`.github/workflows/checks.yml`) | сборка, `npm run check` (описания — по коммитам пуша), `npm test`, `check-api-vercel`, валидаторы |

Хуки включаются сами на `npm install` (скрипт `prepare` → `core.hooksPath =
.githooks`), вручную — `npm run prepare`. Обойти хук (`--no-verify`) можно
только с согласия владельца, и смысла мало: CI проверит то же самое.

⚠️ `install-hooks.mjs` выполняется и на сборке Vercel (`prepare`) — он обязан
молча выходить с кодом 0 без `.git` и при `CI`/`VERCEL`, иначе сломается
выкатка.

## Сторожа

| Сторож | Что не пропускает | Файл |
|---|---|---|
| линтер | небрежности и ошибки хуков React (ESLint: `@eslint/js`, `typescript-eslint`, `react-hooks`; всё — ошибки, не предупреждения); системные окна браузера в `src/` — `window.confirm` / `alert` / `prompt` (`no-alert`, Ф2.17-4б-3: только наш диалог `useConfirm`; правило видит область — `const { confirm } = useConfirm()` проходит) | `eslint.config.js` |
| границы | раздел лезет во внутренности чужого раздела; экран импортирует клиент базы; общий код импортирует экран; циклы; правила новых слоёв §2 | `boundaries.mjs` + `boundaries.config.cjs` |
| токены | сырой цвет (`text-white`, `#fff`, `rgba(…)`), размер `[Npx]`, цвет в `style={{…}}` мимо токенов, токен не в той форме (старое имя `--night-*`, `[var(--color-…)]` в классе, `dark:`) — везде, кроме файла значений `shared/ui/tokens.css` и старого `src/index.css`; общие компоненты `shared/ui` проверяются, как все | `tokens.mjs` |
| размер | файл кода > 400 строк, компонент > 250 (контент и сгенерированное — не в счёт) | `size.mjs` |
| план | пункт `docs/PLAN.md` без поля шаблона, без текста задания, со статусом не из пяти значков, ✅ без даты, «Скиллы: не нужен» без причины | `plan.mjs` |
| секреты | файл окружения `.env*` (кроме `.env.example`) и файл ключа (`.pem`, `.key`, `.p12`, `.pfx`, `.jks`, `.keystore`, `id_rsa`…); ключ по формату — `sb_secret_`, `sbp_`, `AIza…`, `gsk_`, JWT с ролью `service_role`, приватный ключ PEM, `postgres://` с паролем; значение у переменной-секрета (`VAPID_PRIVATE_KEY=…`, `…_SECRET`, `…_PASSWORD`, `…_ACCESS_TOKEN`, `…_API_KEY`). Перед коммитом — версия в индексе, в `npm run check` — файлы в git и новые, которые возьмёт `git add -A`. Списка «к исправлению» нет. Как отличает ключ от примера — ниже | `secrets.mjs` |
| блоки описаний | блок generated в `CLAUDE.md` модуля отстал от кода; у описания с кодом нет блока; указатель «Описание:» ведёт в никуда (лечится `npm run gen:docs`) | `../gen/module-docs.mjs --check` |
| описания | изменён код модуля (`src/`, `api/`), а его описание — нет, и в сообщении нет «описание не меняется, потому что …». Описание файла — указатель `// Описание: …/CLAUDE.md` в первых 20 строках, иначе ближайший `CLAUDE.md` вверх по папкам (у разделов без своего — корневой). Пересборка блока generated правкой не считается | `docs.mjs` |
| тесты | все `scripts/test-*.mjs` по шаблону имени | `tests.mjs` |

**Правило имени тестов:** `test-*.mjs` — только чистые тесты без сети, базы и
секретов (CI запускает их все). Проверка с базой называется `check-*` (так
`test-answermatches-sql` стал `check-answermatches-sql`), браузерная —
`smoke-*`.

⚠️ **Переводы строк.** Git на Windows выдаёт файлы с CRLF, CI (Linux) — с LF.
Две ошибки сторожей были видны только на CRLF (ложный красный у токенов,
непринятая причина у описаний). Сторожей проверяет `scripts/test-checks.mjs` —
каждый случай и с LF, и с CRLF; меняешь сторожа — дополни тест. Генератор
блоков проверяет `scripts/test-module-docs.mjs`.

## Список «к исправлению» (baseline)

Старые нарушения записаны в `baseline/` и работать не мешают; **новые не
проходят**. Список только сужается — по мере переезда разделов (PLAN.md Ф3).

| Файл | Что в нём | 27.09.2026 → 09.10.2026 |
|---|---|---|
| `baseline/eslint.json` | ошибки линтера | 122 в 75 файлах → 104 в 67 |
| `baseline/boundaries.json` | межразделовые импорты, экраны с клиентом базы, циклы | 30 → 27 |
| `baseline/tokens.json` | палитра, `[Npx]`, литералы цвета, `style` | 884 в 190 записях → 197 в 79 |
| `baseline/size.json` | файлы > 400 строк, компоненты > 250 | 27 → 20 |
| `baseline/plan.json` | пункты с «Скиллы: не нужен» без причины | 24 → 24 |

Текущие числа печатает `npm run check`; таблица — снимок для истории.

## Красный — что делать

**«Новые нарушения»** — ты добавил нарушение. Исправь его. В список не
вносить: список для старого, а не для нового.

**«Исправлено … — сузь список»** — ты убрал нарушение из списка (молодец), и
список надо сузить, иначе освободившееся место молча займёт следующее:

```
npm run check:prune
```

`check:prune` только сужает список и никогда не расширяет — запускать можно
всегда. Изменения в `baseline/` коммитятся вместе с исправлением.

**Размер: «файл уже в списке больших и расти не должен»** — решение владельца
(27.09.2026): до переезда большой файл не растёт, его число в списке — планка.
Вынеси новое в отдельный файл. Если дописать внутрь действительно нужно —
планка поднимается осознанно и видно:

```
npm run check:size -- --allow src/features/teacher/TeacherPage.tsx
```

и в сообщении коммита — почему. Так же (`check:tokens -- --allow`,
`check:boundaries -- --allow`) принимается перенос файла со старыми
нарушениями (`git mv` меняет путь, и сторож видит их как новые) — но при
переезде раздела по правилам §12 записей быть не должно: раздел переезжает
чистым.

**Секреты** — значение убери из файла: ключи — в `.env.local` на своей
машине, на сервере — в переменных Vercel. Файл окружения или ключа — `git rm
--cached <файл>` и в `.gitignore`. Если ключ уже ушёл на GitHub (в любой
ветке) или в чат — **замени его у поставщика**: из истории git он не
стирается, а сканирования GitHub у приватного репозитория нет. Значение найденного ключа сторож не печатает — только вид и длину.

Ключ от примера сторож отличает так: ключ — ПОЛНОЕ значение своего формата,
похожее на случайное (`sb_secret_` + 22 + `_` + 8 знаков по документации
Supabase, `AIza` + 35, `gsk_` + 52, `sbp_` + 40). Пример — приставка без
значения или с многоточием (`sb_secret_…`, `AIza…`), заглушка (`<ключ>`,
`[YOUR-PASSWORD]`, `${{ secrets.X }}`, `process.env.X`), выдуманное слово или
ряд (`your_key_here`, `test-secret-123`, `abcdef…`, `xxxx`), строка из знаков
одного вида. Публичное — `sb_publishable_…`, JWT с ролью `anon`, слово
`service_role` в SQL и тексте — не тревога. Ложная тревога — пиши пример с
многоточием; в тестах ключ собирай по частям при запуске (образец —
`scripts/test-checks.mjs`). Обхода пометкой в строке нет намеренно.

**Описания** — обнови `CLAUDE.md` модуля в том же коммите или напиши в
сообщении коммита `описание не меняется, потому что <причина>` (перенос без
изменения поведения, правка опечатки и т.п.). Новое описание — по шаблону
`docs/architecture/module-template.md`.

**Блоки описаний** — `npm run gen:docs` и закоммитить изменённые `CLAUDE.md`.
Указатель в никуда и сломанные метки generated чинятся руками.

**Линтер**: если нарушение на самом деле намеренное — `// eslint-disable-next-line
<правило> -- причина` прямо в коде. Причину пиши всегда: сторож её не
проверяет, это правило для нас.

`--init` (переписать список целиком) — только при появлении сторожа или с
согласия владельца: он принимает в список всё, включая новое.
