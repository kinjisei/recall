# supabase — база: миграции, права, правила таблиц

## Простыми словами

Вся база Recall — Postgres в Supabase: таблицы, правила доступа (кто какую
строку видит) и функции, которые меняют данные (RPC). Её устройство записано
в папке `migrations/` маленькими пронумерованными шагами. Первый шаг
(`0000_baseline.sql`) — снимок базы на 27.09.2026, сверенный с живой; дальше
каждая правка — новый файл.

Баз две: **тестовая** (на ней проверяем всё) и **живая** (на ней ученики).
Шаг сначала катится на тестовую, там проходят проверки, и только потом
владелец сам катит его на живую — пароль от неё вводит руками, нигде он не
хранится. Так правка схемы не может случайно доехать до учеников
непроверенной.

| Что | Где |
|---|---|
| схема, политики, все RPC | `migrations/NNNN_имя.sql` — применённые не правятся |
| данные тестовой базы | `seed.sql` + `node scripts/seed-test.mjs` (настройки как на проде, учитель и 2 ученика) |
| типы базы для клиента | `src/shared/api/database.types.ts` — генерируются, руками не правятся |
| прежняя схема одним файлом | `docs/archive/schema-2026-09-27.sql` — не правится и не заливается |

## Правила, которые нельзя нарушить

**Миграции**

- **Применённая миграция не правится никогда:** базы её уже выполнили,
  правка ничего в них не изменит, а файл начнёт врать. Новое — следующим
  файлом. Текущее состояние видно в самой базе и в `database.types.ts`.
- **Порядок выкатки** (журнал п.47): `npm run db:migrate` (тестовая) →
  проверки и смоуки на тестовой → владелец: `npm run db:migrate:prod` →
  `node scripts/check-db-equal.mjs` (0 расхождений) → push. Клиент зовёт RPC,
  которых иначе на живой базе ещё нет.
- **После миграции — перегенерированные типы в том же коммите:**
  `node scripts/check-types-drift.mjs --write`. Без `--write` та же команда
  сверяет файл со схемой и краснеет при расхождении; приведения
  `supabase.rpc as unknown as …` не нужны — функции есть в типах.

**Права на новые функции — два пояса**

1. **Права по умолчанию** (миграция `0001`): функция, которую создаёт
   `postgres`, с рождения закрыта для `public` и `anon` и открыта
   `authenticated`. Проверено на тестовой базе функцией без единого `revoke`.
2. **Блок-страховка в конце КАЖДОЙ миграции** снимает EXECUTE у `public` и
   `anon` со всех функций, кроме `track_event` (визиты до регистрации).
   `scripts/test-migrations.mjs` (в CI) не пропустит миграцию без блока, с
   изменённым блоком или с кодом после него.

Функцию, которую надо закрыть и от `authenticated` (как `energy_source`,
`notify`) или открыть кому-то ещё, — явным `grant`/`revoke` в той же миграции.

**Таблицы и данные** (сверено со схемой 01.10.2026)

- **Чувствительные записи — только через security-definer RPC** с серверным
  пересчётом: балл задания (`submit_material`), перепроверка слов, квесты,
  тест уровня, тарифы (`admin_*`), занятия (`log_activity`). Прямые
  insert/update на этих таблицах отозваны. Новая таблица с «удобными для
  подделки» полями — сразу так же (корневой `CLAUDE.md`, «Безопасность»).
- **Отвязка отбирает доступ:** политики преподавателя везде проверяют
  `is_student_of`.
- **`profiles` — колоночные гранты:** UPDATE только своих безобидных полей,
  SELECT — только безобидных колонок; секреты (`plan`, `invite_code`,
  `is_admin`) отдают RPC (`get_my_plan`). `select('*')` на `profiles` падает по
  правам — колонки перечисляются явно (`PROFILE_COLUMNS` в `src/lib/profile.ts`).
  Новая колонка без явного `grant` будет невидима клиенту и не сохранится —
  молча.
- **`activity_log` — одна строка на (пользователь, день, тип)**, пишет только
  `log_activity`. Типы: flashcards, reader, pronunciation, conversation,
  writing, grammar, quest, practice, assignment и perfect («идеальный день» —
  не искажает счётчики).
- **При регистрации триггер `handle_new_user`** создаёт профиль и две колоды
  (en и es); пока регистрация закрыта, он же держит белый список
  `allowed_emails` (клиенту невидим). Язык карточки — язык её колоды.
- **`review_states` — расписание у каждого своё** (одна строка на карточку и
  человека), писать можно только по своей или выданной преподавателем
  карточке. Пишет его клиент — это известный остаток (корневой `CLAUDE.md`).
- **Места в тарифе** считает база (`teacher_seats_effective`: Mini 5 /
  Start 10 / Pro 30, в пробный период — `free_teacher_seats()`); привязка
  ученика (`join_teacher`) — под advisory-локом, чтобы двое не заняли одно
  место.
- **Тариф после оплаты меняет только `confirm_payment`** (миграция 0004,
  только владелец, одна транзакция: оплата → продление → заявка → крючок
  рефералки → уведомление → воронка). `payments`, `payment_claims`,
  `personal_codes` закрыты для чтения и записи всем — только RPC; функции с
  чужим uid (`ensure_personal_code`, `after_payment_confirmed`) закрыты и от
  `authenticated`. `admin_set_plan` — ручная правка без оплаты. Правила —
  `src/domains/billing/CLAUDE.md`, проверка — `check-billing.mjs`.
- **Пробный период репетитора — производная, а не ввод** (миграция 0005):
  `profiles.trial_until` репетитору пересчитывают триггеры (включение роли,
  первый ученик, `trial_bonus_days`) по `teacher_trial_end`. Руками её не
  ставить — первый ученик перепишет; подарок — `trial_bonus_days`. Смоук,
  которому нужен «кончившийся пробный», сдвигает регистрацию или включение
  режима, а не одну дату (`smoke-quota-seats`). Правила —
  `src/domains/billing/CLAUDE.md`, проверка — `check-trial.mjs`.
- **Ответ RPC — таблицей (`returns table`), а не `json`**, если его читает
  клиент: тогда `database.types.ts` даёт точный тип строки, и приведение
  `as unknown as` не нужно (архитектура §8). В `plpgsql` с `returns table`
  первой строкой тела — `#variable_conflict use_column`: имена колонок ответа
  (`id`, `plan`) иначе спорят с колонками таблиц в запросах.
- **`content_items` — устаревшая таблица**, приложение её не читает; на ней
  не строить (удаление — PLAN.md Ф3.13).

## Как проверить

- `node scripts/test-migrations.mjs` (чистый, в CI) — блок-страховка на месте,
  baseline не тронут, кириллица и парные `$…$` в SQL.
- `node scripts/check-anon-access.mjs` (тестовая; `--prod` — живая, только
  чтение) — что может вызвать невошедший. Читает `pg_proc.proacl` — именно
  его: у функции без явных прав acl пустой, и это означает «PUBLIC можно», а
  `information_schema` такую строку просто не покажет. Краснеет в обе стороны:
  и если анониму открыли лишнее, и если закрыли `track_event`.
- `node scripts/check-db-equal.mjs` — каталог тестовой = живой (живая — только
  чтение). Слепок каталога (`scripts/_catalog.mjs`: функции с исходниками,
  права вплоть до колонок, политики, ограничения, триггеры) при сжатии старой
  схемы трижды поймал ошибки, а при переходе на миграции показал, что прежний
  слепок не видел колоночных грантов.
- `node scripts/check-types-drift.mjs` — типы = схема тестовой базы.
- `node scripts/check-billing.mjs` — оплата тарифа (миграция 0004): продление,
  права, повторы, заявки — `src/domains/billing/CLAUDE.md`.
- `node scripts/check-trial.mjs` — пробный репетитора и запись без тарифа
  (миграция 0005) — там же.
- `node scripts/check-answermatches-sql.mjs` (вне CI, живая база) — сверка
  ответов в SQL (`norm_typed`) совпадает с клиентом (`lib/text.ts`).

## Решения и почему

- **Два пояса, а не поимённые `revoke`:** новая функция при создании получает
  права по умолчанию (PUBLIC — от Postgres, `anon` — от Supabase). До миграций
  это стоило двух дыр, проверенных на живой базе: `choose_homework_item` была
  открыта анониму от создания до следующей полной заливки, а
  `submit_word_check` (её `drop` + `create` шёл на каждой заливке) — всегда.
  Обе первой строкой проверяют `auth.uid()`, то есть данных аноним не получал.
- **Миграции вместо одного файла схемы** (Ф1.2, архитектура §8): файл
  целиком заливали руками в SQL Editor, и правки то и дело «не доезжали»;
  маленький шаг сначала проверяется на тестовой базе.
- **Пароль живой базы** нужен `npm run db:migrate:prod` и живёт внутри
  секрета GitHub `SUPABASE_DB_URL` — на нём ночной бэкап. Это пароль ОСНОВНОГО
  проекта (не recall-test и не вход на supabase.com). Сбросил пароль
  (Supabase → Settings → Database) — обнови и секрет и запусти бэкап руками
  (Actions → Run workflow), иначе ночью он упадёт. Восстановление —
  `docs/backup-restore.md`.
